Modern Semantic RAG — teaching the search engine what words mean

Notebook 1 built a search engine that only matches exact words, and it flat-out failed on real on-call language — a query like "the message bus is falling behind" scored a flat 0.000 against the Kafka runbook because the two share zero words. This notebook rebuilds retrieval around meaning instead of spelling: embeddings that understand synonyms, a fast index to search them at scale, a second-pass re-ranker that fixes the mistakes the first pass makes, a hybrid search that gets exact error codes back, and metadata filters that stop the system from searching the wrong runbooks entirely.

Problem
If we change the runbooks, the chunking, and the search method all at once, and results improve, we won't know which change actually helped.
Why
This is basic experimental hygiene — change one variable at a time. Otherwise any improvement is a coincidence you can't explain or reproduce.
What
The same five SRE runbooks (payment, orders, login, Kafka, Kubernetes) are cleaned and cut into the same 60-word overlapping chunks as Notebook 1. The same 10 test questions come back too — 5 "lexical" ones that share words with the runbook, 5 "semantic" ones that are paraphrases with almost no shared words.
How
The cleaning function and the chunking function are copy-pasted unchanged from Notebook 1. Only the next section — how a chunk gets turned into numbers — is allowed to change.
Plain English

It's like re-running the same cooking test with the same ingredients and the same oven, changing only the recipe technique you're trying to evaluate.

The test set that exposes everything

5 "lexical" questions like "Why is Kafka consumer lag increasing?" share real words with the Kafka runbook. 5 "semantic" questions like "The message bus is falling behind" mean the same thing but share almost none. This split is the single most useful idea in the whole notebook — it tells you exactly which half of the problem a change actually fixed.

Section 3 — Sentence embeddings: teaching the machine what words mean

Cell 11 · swapping "count the words" for "understand the sentence"

3all-MiniLM-L6-v2: turning a sentence into a point in space
Problem
TF-IDF has no concept of synonyms. "Message bus" and "Kafka" are two completely different words to it, even though an SRE knows they mean the same thing here.
Why
Real people don't repeat a runbook's exact vocabulary when they're paging at 2am. If search only works for people who already know the right words, it isn't useful during an actual incident.
What
An embedding is a list of numbers — a "GPS coordinate for meaning" — that a trained neural network assigns to a piece of text. Texts with similar meaning land at nearby coordinates, even if they don't share a single word. A sentence-transformer is the model that produces these coordinates; "all-MiniLM-L6-v2" is a small, fast one that outputs 384 numbers per chunk.
How
Nothing about the surrounding pipeline changes — same chunks, same "compare with cosine similarity" math as Notebook 1. Only the function that turns text into numbers is swapped: instead of counting words, every chunk gets encoded into a 384-number vector by the transformer model. All vectors are also scaled to the same length ("normalized"), which is what lets the next section's fast index treat "closest" and "most similar" as the same question.
Plain English

Imagine giving every sentence in the world a GPS coordinate based on what it means, not what letters it contains. "The message bus is falling behind" and "Kafka consumer lag is increasing" would land right next to each other on that map, even though they don't share a single important word.

Section 4 — FAISS: a fast filing system for meaning-coordinates

Cell 20 · replacing the for-loop with a purpose-built vector index

4Same search, engineered to actually scale
Problem
Notebook 1's search was a Python for-loop comparing the query against every single chunk, one at a time — correct, but it gets painfully slow once you have more than a handful of documents.
Why
A real runbook library has thousands of pages, not five. At even 100,000 chunks, a plain for-loop in Python becomes too slow to answer a query in real time.
What
FAISS is a library (built by Meta) purpose-built to store meaning-coordinates and find the closest ones fast — it's the same core idea a vector database uses under the hood. We use IndexFlatIP: it still checks every stored vector (so the result is mathematically identical to the old for-loop), just implemented in fast compiled code instead of a Python loop.
How
All the chunk vectors are loaded into the index once. From then on, a search just asks FAISS for the top few closest vectors, and FAISS hands back their position numbers and scores — which get mapped back to chunk IDs. The notebook double-checks that FAISS's answer for a sample query is identical, row for row, to the old hand-written numpy search.
Plain English

If TF-IDF's for-loop is checking every filing cabinet in a building one by one, FAISS is a librarian who has already organized everything for fast lookup. For small archives it's overkill; for a whole company's runbooks, it's the only way search stays instant.

Caveat

Approximate indexes trade accuracy for speed — they can silently miss the true best match. This notebook's 10 chunks don't need that trade-off, so it uses the exact index. Production systems at scale (like pgvector's HNSW index in Notebook 3) do make this trade, and the recall loss becomes something you have to measure, not assume away.

Section 5 — Cross-encoder re-ranking: a second, stricter look

Cell 22–24 · fixing "vocabulary collision" mistakes that embeddings alone still make

5Bi-encoder vs. cross-encoder
Problem
Even with good embeddings, one failure survives from Notebook 1: "Customers see failures at checkout" retrieved the Kubernetes runbook instead of payment-service, because the word "failures" is strong there.
Why
The embedding model encodes the question and every chunk separately, then compares the resulting coordinates. It never actually reads the question and a specific chunk side by side — so subtle wording overlaps can still fool it.
What
The model we've used so far (a bi-encoder) is like two people separately taking notes on two different documents, then comparing notes afterward — fast, because chunk notes can be prepared ahead of time. A cross-encoder instead reads the question and one candidate chunk together, side by side, in the same pass — much more accurate, but it has to be done fresh for every single pair, so it can't be pre-computed and doesn't scale to a whole corpus.
How
The standard two-stage pattern used by Google, Bing, and every serious search system: Stage 1 — cheaply retrieve a wide pool (top-20) using the bi-encoder + FAISS. Stage 2 — run the slower, more accurate cross-encoder on just those 20 candidates, and keep only the new top 3. You get the speed of the bi-encoder and the accuracy of the cross-encoder, by only paying the cross-encoder's cost on a tiny shortlist.
Plain English

Bi-encoder: two students each summarize a different book, then you compare summaries. Cross-encoder: one student reads both books side by side and gives you a direct verdict. The second is more reliable but far slower if you had to do it for every book in the library — so you use the fast method to find the 20 most promising books, then bring in the careful reader only for those 20.

5.1The bill: how much slower is re-ranking?
Problem
Better accuracy isn't free — re-ranking 20 candidates means 20 extra full model passes on the critical path of every single query.
Why
You should never add a component like this without measuring what it costs. "More accurate" and "worth it" are different questions.
What
Latency: how long, in milliseconds, a user waits for a result.
How
The notebook times the bi-encoder-only search and the full bi-encoder + cross-encoder search over several runs and reports the ratio.
Trade-off

Cross-encoder re-ranking is measured as several times slower than bi-encoder search alone (tens to low-hundreds of milliseconds vs. single-digit milliseconds). The notebook's verdict: during an actual incident, an SRE will happily wait an extra 300ms for a materially better answer — but this is a product decision, not a free upgrade, and it belongs on the latency budget.

Section 6 — Hybrid search: BM25 + embeddings together

Cell 28–31 · fixing the new blind spot embeddings introduced

6Embeddings are bad at exact identifiers
Problem
Embeddings have their own blind spot — the mirror image of TF-IDF's. Ask for the literal error string NotEnoughReplicasException and MiniLM gives you something merely "similar in topic," not an exact hit.
Why
This matters enormously for SRE work. On-call engineers paste exact pod names, exception classes, and topic names — they want that literal token found, not a topically-related paragraph.
What
BM25 is a modernized version of TF-IDF's keyword counting (it accounts for document length and diminishing returns on repeated words) — it's precise on exact strings the way embeddings are precise on meaning. Hybrid search runs both a keyword scorer and an embedding scorer and blends their opinions instead of picking one.
How
Two ways to combine scores are shown. Weighted blend: rescale both scores to 0–1 first (because BM25's scores are unbounded, roughly 0–20+, while cosine scores are bounded −1 to 1 — adding them unscaled would let BM25 dominate arbitrarily), then mix them with a dial called alpha: alpha × embedding_score + (1 − alpha) × BM25_score. Reciprocal Rank Fusion (RRF): ignore raw scores entirely and fuse by each result's rank position instead — more robust, no rescaling needed.
Plain English

Embeddings are a colleague who's great at grasping the gist of what you mean but bad with exact names and numbers. Keyword search is the opposite — terrible at paraphrases, perfect at exact strings. Hybrid search asks both colleagues and merges their answers.

Why

What
Alpha is a dial from 0 to 1: 0 means "trust only keyword matching," 1 means "trust only meaning matching," and anything in between is a blend.

Read this carefully

If the lexical and semantic curves slope in opposite directions as alpha changes, that's the actual trade-off of hybrid search: keyword matching wins on literal queries, embeddings win on paraphrases, and alpha buys one at the expense of the other. The best alpha is a property of your query mix, not a universal constant — don't copy someone else's alpha from a blog post. Build an eval set from real on-call questions first.

Section 7 — Metadata filtering: don't even look at the wrong runbooks

Cell 34 · using known facts about the incident to narrow the search up front

7Pre-filter, don't post-filter
Problem
Every search so far checks all chunks, every time. But during a Kafka incident, searching the login runbook isn't just wasted work — it's a chance to confidently retrieve something plausible-but-wrong.
Why
If the incident system already knows the affected service (e.g. from an "Incident Bundle" that says service: kafka-cluster), ignoring that fact and searching everything is throwing away free, reliable information.
What
Pre-filtering means narrowing the candidate set before searching, so search only ever considers allowed chunks. Post-filtering means searching everything first, then throwing away results that don't match — which has a real bug: if all the top results happen to belong to other services, you're left with nothing.
How
A true/false mask marks which chunks belong to the allowed service(s); the search only runs over the rows where that mask is true. Real production vector databases do the same thing natively (in pgvector, this is a SQL WHERE clause running alongside the similarity search).
Plain English

Post-filtering is searching the whole building for a red folder, then throwing out anything that's not red — and if the whole floor you searched happens to have no red folders, you come back empty-handed. Pre-filtering is only opening the red filing cabinet in the first place.

Real notebook example

Query: "How do I restart it?" — deliberately vague, exactly how people talk mid-incident.

No filter: ambiguous — every runbook has some kind of restart procedure, so the top result could be any of the five services.
Pre-filtered to payment-service: returns payment-service restart steps specifically.
Pre-filtered to kafka-cluster: returns Kafka broker restart steps specifically.

The vague question becomes answerable the moment you supply one known fact.

Tip

In a production incident system, structured fields like service, severity, and deployment aren't just information for the LLM to read — they're a retrieval filter. Using them cuts both cost (searching fewer chunks) and hallucination risk (never even considering the wrong runbook). Filtering is free accuracy whenever you already have structured context.

Section 8 — The full pipeline, assembled

Cell 37–41 · every component wired together in production order, and the trap that's still open

8Filter → hybrid retrieve → re-rank → prompt → answer
Problem
Every component built so far — embeddings, FAISS, cross-encoder, hybrid fusion, filtering — has been shown separately. A real system needs them working together, in the right order.
Why
The order matters: filtering first narrows the field cheaply; hybrid retrieval next casts a wide, fast net over what's left; re-ranking last spends its expensive accuracy only on a small shortlist. Doing it in a different order wastes work or loses accuracy.
What
One function, rag_pipeline(), chains: metadata pre-filter → hybrid (BM25 + embeddings, fused by RRF) retrieval of a wide candidate pool → cross-encoder re-ranking down to the final top-k. A second function, build_prompt(), wraps those results in the same "answer only from this context, cite sources, refuse if you don't know" prompt template as Notebook 1.
How
Three test questions each exercise a different path: a paraphrase with no filter, a vague question with a service filter applied, and — critically — a genuinely out-of-scope question about a mail server TLS certificate, which no runbook in this corpus covers.

8.1The trap: top-k search can never say "I don't know"
Problem
The pipeline was asked "How do I rotate the TLS certificate on the mail server?" — there is no mail-server runbook in this corpus at all. The correct answer is "I don't have a runbook for that." Instead, retrieval confidently returned three chunks, and the mock LLM dutifully produced commands from them.
Why
This is not the LLM's fault — it did exactly what it was told, using the context it was handed. The retrieval layer lied first. "Top-k" literally means "always return k results," and ranking is relative — the system will happily hand you the least-bad chunk out of a corpus of entirely irrelevant chunks. Nothing about a top-k search ever asks "is this actually relevant at all?"
What
A relevance threshold is an absolute score floor. Retrieve the top-k as usual, then throw out anything scoring below the floor. If nothing survives, return zero context and let the model refuse honestly.
How
The notebook prints the top relevance score for six probe questions (three clearly in-scope, three clearly out-of-scope) so you can see where a gap exists between the two groups, then asks you to pick a threshold value that sits in that gap and re-run to check that every question is now handled correctly.
Plain English

Top-k search is like a helpful but overly agreeable assistant who, when asked to name your best restaurant option, will name something even if every restaurant in town is terrible — because "best of the options given" was the actual instruction. A threshold teaches the assistant to say "honestly, none of these are good" when that's the truth.

Danger — this is the failure mode to internalize

Without a threshold, a RAG system can never refuse on its own. It will always find a "closest" runbook, cite it confidently, and generate a plausible-sounding but wrong answer. This is the classic hallucination path, and it starts in retrieval, not in the language model.

The gap you're looking for

In-scope questions like "How do I restart the payment service?" and "The message bus is falling behind" score clearly positive. Out-of-scope questions — the TLS certificate one, a refund-policy question, even "How do I bake sourdough bread?" — score noticeably lower. A threshold placed between the two groups turns "always answer something" into "answer only when actually confident, refuse otherwise."

Trade-off — the same dial as alerting thresholds

Set the threshold too high and the system refuses questions it could have answered (false negatives). Set it too low and the hallucination path stays open (false positives). The notebook also challenges you to try to break your own threshold with a tricky out-of-scope question that happens to share a word with a runbook (e.g. "How do I restart my laptop?"). If one clever question defeats a hand-picked number, that's the argument for calibrated confidence scoring in production, rather than a single constant.
