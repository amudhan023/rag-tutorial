What is RAG, really?

Problem: AI models don't know your private documents and will confidently guess if you ask about them.

Why: Retraining a model on your documents is slow and expensive.

What: Instead, find the relevant paragraphs yourself and paste them into the question you ask the model — an "open book exam" instead of a "closed book exam."

Your question
↓
Find matching paragraphs (Retrieval)
↓
Paste them into a prompt (Augmentation)
↓
AI answers using only that text (Generation)

Chunking & overlap

Problem: Whole documents are too big and unfocused to search well.

What: Cut documents into small overlapping windows of text so search results are precise, and important phrases never get sliced in half at a chunk boundary.

Embeddings — turning text into numbers

Problem: Computers can't compare "meaning" directly.

What: An embedding is a list of numbers standing in for a piece of text, built so that texts with similar meaning end up with nearby numbers. TF-IDF counts exact words; neural embeddings learn to represent meaning, including synonyms.

Cosine similarity — how "close" is measured

Problem: Given two lists of numbers, how do you decide if they mean similar things?

What: Picture each list of numbers as an arrow. Cosine similarity measures the angle between two arrows — a small angle (pointing the same way) means very similar; a wide angle means unrelated. It ignores how long each arrow is.

Vector databases — not as magical as they sound

Problem: "Vector database" sounds complicated.

What: Underneath, it does two jobs: store (vector + info about it), and given a new vector, return the closest matches. A plain Python list with a for-loop already does this — real databases (FAISS, pgvector) just make it fast at millions of rows using indexes like HNSW.

🧩

Why exact word-matching isn't enough

Problem: "The message bus is falling behind" means the same thing as "Kafka consumer lag is increasing" — but shares zero exact words.

What: Word-counting methods (TF-IDF, keyword search) score this pair at ≈0.000 similarity. Meaning-based embeddings fix it by placing synonyms near each other in number-space, regardless of the exact words used.

Re-ranking — fixing false matches

Problem: "Customers see failures at checkout" can retrieve a Kubernetes document just because both mention the word "failures," even though it's about a payment issue.

What: A first-pass search casts a wide, fast net (bi-encoder); a slower, smarter second pass (cross-encoder) reads the query and each candidate together and re-orders them by true relevance, catching matches that share words but not context.

🤝

Hybrid search — best of both worlds

Problem: Keyword search is great at exact terms (error codes, product names); meaning-based search is great at paraphrases. Neither wins every case.

What: Run both searches, then blend their rankings into one combined result — either by weighting scores, or with Reciprocal Rank Fusion (RRF), which combines rankings without needing the two searches' scores to be on the same scale.

Approximate search (HNSW) — speed vs. accuracy

Problem: Checking every single stored vector one-by-one (brute force) is too slow once you have millions of documents.

What: HNSW is an index that finds almost always the same top matches as brute force, but far faster, by pre-building shortcuts through the data. The trade-off is tunable — search wider (slower, more accurate) or narrower (faster, occasionally misses a match).

How do you measure if search is any good?

Problem: "It feels like it's working" isn't good enough for a production system.

What: Build a small test set of real questions with known correct answers, then score every search configuration against it with metrics like hit@1 (did the top result match?), recall@k, MRR, and nDCG — so improvements are proven with numbers, not vibes.

🚨

Knowing when to say "I don't know"

Problem: If someone asks an out-of-scope question, search still returns its "closest" match — even if nothing in the documents is actually relevant — and the AI may confidently answer from a bad match anyway.

What: In-scope questions score noticeably higher than out-of-scope ones. Setting a similarity-score threshold, and explicitly permitting the model to refuse, turns silent guessing into an honest "I don't have information on that."
