Production RAG: PostgreSQL, pgvector, and the numbers that keep it honest

§0 Why bother with a real database at all?
Problem Notebook 2's search engine lived entirely inside a running Python process — a Python list of vectors plus a FAISS index sitting in RAM. The moment that process restarts (a crash, a deploy, a laptop closing), every embedding is gone and has to be recomputed from scratch. At 3am, during an incident, "restart the search service and wait five minutes while it re-embeds everything" is not an acceptable answer.
Why A demo only has to survive one session. A production service has to survive crashes, deploys, multiple servers reading the same data at once, and someone needing to filter results by service = 'payment' without writing custom code for it. FAISS was never designed to solve any of that — it is a very good index, not a database.
What Think of the difference like a chef's private notecards versus a restaurant's actual recipe binder kept in the office safe. The notecards (FAISS) are fast to flip through, but if the chef goes home, they go with them. The binder (a database) is durable — it survives staff turnover, it's the one shared copy everyone works from, and you can flip straight to "all seafood dishes" instead of reading every page. This notebook swaps the notecards for PostgreSQL, a real database, extended with pgvector — a plugin that teaches Postgres how to store and search the numeric "meaning fingerprints" (embeddings) from Notebook 2 as a native column type.
How The notebook doesn't change what gets embedded or how similarity is measured — that logic from Notebook 2 stays the same. What changes is where it all lives: chunk text, its embedding, and metadata like service and severity move into one row of one Postgres table, instead of three parallel Python lists that can silently drift out of sync with each other.
Plain English

FAISS is like a search engine's fast cache that lives only in your computer's memory — great while it's running, gone the instant power is cut. A database is the permanent filing cabinet: slower to add a new sheet of paper to, but it's still there tomorrow, and two people can open different drawers of it at the same time without stepping on each other.

What a database buys you, concretely

The notebook lists five things FAISS cannot give you that Postgres can: durability (survive a restart without re-embedding), transactions ("either the whole runbook and its metadata save together, or neither does" — no half-written rows), rich filtering (a real WHERE service = 'payment' AND updated_at > now() - interval '90 days' instead of hand-slicing numpy arrays), one source of truth (text, vector, and metadata in the same row — no separate "vector store" that can fall out of sync with the "metadata store"), and operational maturity — backups, replication, monitoring your organization already knows how to run.

Honest trade-off

A dedicated vector database (Milvus, Qdrant, Pinecone) will out-perform pgvector at truly massive scale. But pgvector's real pitch is that it's already in your stack — for an incident-response tool handling thousands of runbook chunks, not billions, "one fewer system to keep alive during an outage" beats squeezing out the last drop of raw speed.

§2 Designing the table: every column is a decision
Problem A database table isn't just "a place to dump data" — get the columns wrong and you bake in bugs that only surface months later, when someone changes the embedding model and nothing warns them the old and new vectors are now incomparable.
Why Notebook 1's quiz raised exactly this failure mode as a thought experiment: mix vectors from two different embedding models in the same search space and you get confident, wrong answers with no error message. A well-designed schema turns that theoretical risk into something you can catch with one query.
What The table runbook_chunks stores one row per chunk of runbook text, with the chunk's content, its embedding, and metadata to filter on, all side by side. An index in a database means exactly what an index means in the back of a textbook: instead of Postgres reading every single row to answer "show me all payment-service chunks," it flips straight to the right pages.
How The schema fixes the embedding's size (384 numbers) as part of the table definition, stamps every row with which embedding model produced it, stores service and severity as their own filterable columns rather than buried in a text blob, keeps a content_hash fingerprint of the text for deduplication, and records updated_at so stale runbooks can be flagged.
Plain English

Imagine designing a library card for every book: title, shelf location, and a barcode. If you forgot to record "which edition," a librarian pulling the wrong edition during a fire drill wouldn't even know it was wrong. Every column here exists to prevent one specific future mistake.

§3 Loading the runbooks — and never paying twice for the same text
Problem Ingestion pipelines get re-run — a deploy retriggers them, someone fixes a typo in one runbook and reruns the whole batch. Run a naive ingestion script twice and you get every chunk duplicated, which quietly poisons search results: the same chunk now occupies two, three, four of your top-k slots instead of leaving room for genuinely different evidence.
Why Turning text into an embedding costs real compute time and, with a hosted embedding API, real money. Re-embedding thousands of unchanged runbook chunks every time a deploy pipeline runs is waste that compounds — the notebook's own framing: "at scale this is the difference between $0.20 and $200."
What The fix is making ingestion idempotent — a fancy word for "running it twice has the same effect as running it once." The database is told: if a row with this chunk_id already exists, only touch it if the content actually changed (checked via the content_hash fingerprint); otherwise leave it alone.
How Same five runbooks, same cleaning and chunking as Notebooks 1–2, but written with an ON CONFLICT ... DO UPDATE clause guarded by WHERE content_hash IS DISTINCT FROM the new hash — so an unchanged chunk is skipped entirely, and a genuinely edited chunk gets its embedding recomputed and its updated_at timestamp bumped.
Plain English

It's a fingerprint check at the door. If the runbook text coming in has the exact same fingerprint as what's already stored, the database says "already got this one" and skips the expensive work of re-embedding it. Only genuinely new or edited text does the expensive work.

Worked example: re-running ingestion on an unchanged corpus

The notebook re-runs ingestion a second time over the same 5 runbooks and checks, chunk by chunk, whether the stored content_hash matches the freshly computed one. Every chunk that matches is an embedding call avoided entirely. The notebook's own comment on the payoff: "Embedding calls avoided: (unchanged count) — at scale this is the difference between $0.20 and $200." Row count after the re-run is identical to before — nothing was duplicated.

§4 Asking Postgres "which chunks are closest in meaning?"
Problem In Notebook 2, doing vector similarity search plus filtering by service meant slicing numpy arrays by hand in Python and juggling candidate ID lists. That's extra code to get wrong, and it's a second system that has to agree with the database about what's true.
Why pgvector adds vector math directly into SQL, so "find the closest vectors" and "only look at payment-service rows" can be answered by the database in a single query — the same engine, the same query plan, no hand-off between two systems.
What pgvector adds three "distance operators" — symbols that mean "how far apart are these two vectors." Cosine distance (<=>) is the safe default for text — it compares direction, not magnitude, which matches how sentence embeddings work. The others exist for special cases: negative inner product (<#>) is a faster equivalent when vectors are already unit-length, and Euclidean (<->) is rarely the right choice for text.
How The query text is embedded into a vector, then ORDER BY embedding <=> query LIMIT k sorts every row by distance, closest first, and keeps the top k. An optional WHERE clause (built up dynamically from whichever filters were requested — service, a recency window) narrows the search before the sort even happens, using the B-tree indexes from Section 2.
Plain English

Distance, not similarity, is what gets sorted — 0 means "pointing in exactly the same direction" (identical meaning) and larger numbers mean "further apart in meaning." Sorting ascending by distance puts the closest matches first. The notebook flags a real, easy-to-make bug here: get the sort direction backwards and the query still runs without error — it just silently returns the least relevant chunks first.

Query: "The message bus is falling behind" — even though the query never says "Kafka," a plain vector search over all 5 runbooks ranks the Kafka runbook's chunks highest, because embeddings capture meaning, not keywords. Run the follow-up query "How do I restart it?" with a service='payment-service' filter attached, and the same search engine now only considers payment-service rows — the ambiguous pronoun "it" resolves correctly because the filter did the disambiguation, not the model.

Why this beats Notebook 2's approach

There, metadata filtering meant hand-slicing numpy arrays and threading candidate-ID lists through the code. Here it's one WHERE clause the query planner optimizes using a real index. Filtering and vector search living in the same engine is the single most practical argument for pgvector.

§5 HNSW: trading a little accuracy for a lot of speed
Problem Every search so far did a sequential scan — Postgres compared the query vector against literally every single row before sorting. That's exact, but the cost grows in direct proportion to the number of rows. At 10 runbook chunks that's instant. At millions of chunks across a whole organization's runbooks, it's not.
Why A search assistant someone is using mid-incident cannot wait seconds for every query while the database walks the entire table. Production systems need sub-linear search — time that grows much more slowly than the data does.
What HNSW (Hierarchical Navigable Small World) is an index that pre-builds a layered map of "which vectors are near which other vectors," and walks that map instead of checking every row. Picture a highway system with occasional exits, instead of walking down every single street of every neighborhood to find one house: you take the highway to roughly the right district, then step down to local streets only at the end. It's dramatically faster — but because it's a shortcut, it's approximate: it can occasionally miss the one true best match that an exhaustive street-by-street search would have found. That's called approximate nearest neighbor search, and the fraction of true matches it still finds is called recall.
How Three knobs control the trade-off. Two are fixed when the index is built (m — how many highway connections each vector gets; more means better recall but a bigger, slower-to-build index — and ef_construction — how thoroughly the map is built in the first place). The third, ef_search, is a runtime dial: how many candidates the search explores per query. It can be tuned per query with no index rebuild, and it's the one an operator actually adjusts in production.
Plain English

HNSW is GPS turn-by-turn directions instead of driving down every street in the city. It'll almost always get you to the right house fast — but very occasionally it takes a route that misses the absolute closest one by a house or two. ef_search is "how many alternate routes GPS considers before picking one" — consider more routes, get closer to the true best answer, but the search takes longer.

Honest caveat baked into this notebook

The real runbook_chunks table only has ~10 rows. HNSW on 10 rows is meaningless — Postgres will often just ignore the index and do a sequential scan anyway, because at that size a full scan is cheaper. That's correct behavior, not a bug. So the actual recall/latency measurement is done separately, against 50,000 synthetic vectors, where the trade-off is big enough to see.

The scary part: recall < 1.0 fails silently

Recall below 1.0 means the right chunk sometimes just isn't in the candidate set the search engine returns — no error, no log line, nothing. The system looks completely healthy. The LLM downstream just answers using whatever chunks it was handed, confidently, from an incomplete set of evidence. Production practice: measure recall on your actual data, and re-measure after the corpus grows — the shape of the graph changes as more vectors are added.

§5.2 The benchmark trap: how the test data itself decided the result
Problem While building the HNSW measurement above, the first attempt used pure random vectors for the synthetic 50,000-row corpus — the obvious, easy choice. It produced a wildly different, and wrong, conclusion.
Why Any benchmark — including vendor marketing benchmarks — can be accidentally (or conveniently) rigged by choosing unrealistic test data. This is the single most important methodological lesson in the whole notebook: it isn't enough to run the "right" measurement code, the data you feed it has to resemble reality.
What Real sentence embeddings cluster — sentences about Kafka land near other sentences about Kafka in the 384-dimensional space. Independent random Gaussian vectors don't cluster at all; in high dimensions, random vectors end up almost equally far from everything (the "curse of dimensionality"). HNSW's whole trick depends on there being real neighborhood structure to navigate — feed it a structureless cloud of random points and the greedy graph walk has nothing to follow.
How The notebook regenerates the synthetic corpus two ways for comparison: (A) pure random Gaussian vectors, and (B) vectors built from 200 topic centroids plus a small amount of noise — mimicking how real embeddings cluster by topic. It even measures peak cosine similarity within each set as a sanity check before running any search at all: random vectors top out around 0.23 similarity (nothing is really close to anything), clustered vectors reach 0.5–0.9 (matching what real sentence embeddings look like).
Plain English

Testing a highway shortcut system by scattering houses uniformly at random across an infinite desert, with no towns or neighborhoods, tells you nothing about how it performs on an actual city with real neighborhoods. The shortcuts only help when there's structure to exploit.

The transferable lesson

A benchmark on unrealistic data doesn't produce a slightly-wrong answer — it produces a confidently inverted one. A reader who ran only the random-vector version would reasonably (and wrongly) conclude HNSW is unusable and abandon it. Before trusting any approximate-search benchmark, check whether the test vectors actually have the clustering properties of the real corpus. When this gets tuned for a real system later, the sweep has to run against embeddings of the real documents — never synthetic stand-ins.

§6 Hybrid search as one SQL query, not two systems
Problem Notebook 2 ran keyword search (BM25) in a separate Python process from vector search, then fused the two rankings together in numpy. Two systems means two places for bugs to creep in, and two things that can silently drift out of sync as the corpus changes.
Why Postgres already has native full-text search built on the GIN index created back in Section 2. If both keyword ranking and vector ranking can run in the same database, the fusion logic can live there too — one query, one system of record.
What The query is built from CTEs (Common Table Expressions) — think of a CTE as a labeled intermediate step in a recipe: "first, do this and call the result Step A; then do that and call it Step B; now combine A and B." Each CTE here computes one retriever's ranking (one for vector similarity, one for keyword relevance), and a final step combines them. The combination method is Reciprocal Rank Fusion (RRF): instead of trying to average two scores that live on completely different, incomparable scales (a cosine distance and a keyword-rank score), RRF only looks at each retriever's rank — 1st place, 2nd place, 3rd place — and rewards items that rank well on either or both lists.
How One CTE ranks chunks by vector distance using ROW_NUMBER() OVER (ORDER BY ...) — a window function, which just means "compute a rank for each row without collapsing the table into a single summary number." A second CTE does the same using Postgres's keyword relevance function (ts_rank) over the full-text index. The two rank lists are then combined with a FULL OUTER JOIN (keep a chunk even if only one retriever found it) and scored as 1/(60 + rank) summed across both lists — the standard RRF formula, where 60 is a smoothing constant. Sort by that combined score, and the top results are returned.
Plain English

Imagine two judges scoring a talent show independently — one only cares about vocal technique, the other only cares about audience reaction. Instead of trying to average "8.2 out of a weird technical scale" with "94% audience approval" (numbers that mean nothing compared to each other), RRF just asks each judge for their ranked list — 1st place, 2nd, 3rd — and combines the rankings. A contestant who's #1 on one judge's list and #4 on the other's beats someone who's #2 on both, roughly, but the exact math rewards strong rank on either list heavily.

Two queries, two different winners

Query "NotEnoughReplicasException" — an exact log identifier. Keyword search nails it immediately; vector search is vaguer about an obscure token like this. Query "The message bus is falling behind" — a paraphrase with no shared words with the Kafka runbook text. Vector search wins here; keyword search may not even return the chunk. RRF blends both without either retriever dominating by default — a chunk that only one retriever found (a NULL on the other rank column) can still surface if its single ranking is strong enough.

Why rank fusion instead of blending raw scores

ts_rank and cosine similarity live on completely different, non-comparable scales, and ts_rank's values shift as the corpus grows (it's influenced by term frequency across the whole table). Rank-based fusion is immune to both problems, which is why it's the default choice in production hybrid-search systems — one less thing to re-tune every time the corpus changes.

§7 Grading retrieval quality with real metrics, not a gut feeling
Problem Earlier notebooks used a single crude metric, hit@1: was the very top result correct, yes or no? That only answers one narrow question and throws away everything about how the rest of the ranked list looked.
Why Different failure modes matter for different reasons. A wrong chunk mixed into the prompt can cause the LLM to hallucinate a remediation step — and remediation steps get executed during a live incident. A missed piece of evidence is also bad, just differently bad. One number can't capture both.
What Four standard information-retrieval metrics, each answering a different question: Precision@k — of the k results actually returned, what fraction were relevant? (catches "prompt pollution," irrelevant junk crowding the context). Recall@k — of everything relevant that exists, what fraction did the search find? (catches missed evidence). MRR (Mean Reciprocal Rank) — how far down the list was the first relevant result? (does the user see something useful immediately, or have to scroll). nDCG@k (Normalized Discounted Cumulative Gain) — are the relevant results bunched near the top, position-weighted? (an overall ranking-quality score from 0 to 1, where 1.0 is a perfect ordering).
How Each metric is implemented from scratch in a few lines of arithmetic over a list of 0/1 relevance labels (1 = this ranked result is actually relevant). Precision is just the fraction of 1s in the top k. Recall divides the 1s found by the true total number of relevant chunks in the corpus. MRR finds the position of the first 1 and takes its reciprocal (rank 1 → score 1.0, rank 2 → 0.5, rank 10 → 0.1 — a steep penalty for burying the good result). nDCG discounts each relevant result by log2(rank + 1) — a hit at position 1 counts fully, a hit at position 10 counts much less — then normalizes against the best possible ordering so scores are comparable across different questions.
Plain English

Precision is "how much of what I handed you was actually useful." Recall is "of all the useful stuff that existed, how much did I actually find." MRR is "how long did you have to scroll before seeing something good." nDCG is a single overall report card that rewards good stuff being near the top and penalizes it being buried.

Sanity-checking the formulas before trusting them

The notebook runs each metric against hand-built toy examples before using them for anything real — never trust a metric you haven't tested. A ranking with all 3 relevant results first scores nDCG@3 = 1.000 (perfect). The same 3 relevant results pushed to dead last score nDCG@3 = 0.000 (worst possible). A mixed case with the first relevant result at position 2 scores MRR = 0.500 (matches 1/2 exactly, as expected).

Which metric matters most for an SRE runbook assistant

Mostly precision. Only 3 chunks typically fit in the prompt, so a wrong chunk squeezed into that small budget is a real cost — an invitation for the LLM to hallucinate a step that might get executed live. Recall still matters (missing the one right runbook is bad too), but for a small, fixed context window, precision is usually the tighter constraint.

A labelled evaluation set — 13 real questions, three categories

Ground truth here is document-level: any chunk from the expected runbook counts as relevant (cheaper to label than marking individual chunks, a real trade-off the notebook names explicitly). Questions are split into three categories to see where each retriever actually earns its keep: lexical (shares words with the runbook, e.g. "Why is Kafka consumer lag increasing?"), semantic (a paraphrase with no shared vocabulary, e.g. "The event pipeline stopped delivering data" for the same Kafka runbook), and identifier (an exact code or error string, e.g. "NotEnoughReplicasException in producer logs"). The vector-only retriever and the hybrid (RRF) retriever from Section 6 are scored side by side on identical questions using every metric above, then broken down by category — the pattern that emerges echoes Notebook 2's finding: vector search alone is strong on semantic paraphrases but weaker on exact identifiers, and hybrid closes that gap without giving up the semantic strength.

Sample-size honesty

13 questions over roughly 10 chunks is a small evaluation set — a single question flipping from wrong to right moves the mean score by roughly 0.08. Treat these particular numbers as an illustration of the method, not a definitive scoreboard. The transferable practice: label a real set, break results down by failure category, and always compare retrievers on identical questions. For a real deployment, harvest evaluation questions from actual incident conversations — that's the only way the question distribution matches what production traffic will actually look like.

§8 Observability: catching failures that look like success
Problem A bad retrieval doesn't crash. It doesn't throw an error. It just quietly hands the LLM the wrong evidence, and the LLM still writes a fluent, confident-sounding answer. Every other service already gets instrumented (logs, metrics, alarms) — retrieval, which fails silently by nature, needs it even more.
Why When an engineer later says "the assistant gave me a wrong remediation step," the first question a postmortem needs answered is: was retrieval wrong, or was the LLM wrong given genuinely correct context? Without a record of exactly what was retrieved, for exactly which query, at exactly what time, that question is unanswerable — and the postmortem wastes time arguing about it instead of fixing it.
What Four signals worth emitting on every single query: latency percentiles per stage (embed, search, re-rank) — not just the average, because averages hide the tail; a top relevance score per query (the drift alarm carried over from Notebook 2); the result count after thresholding (a rise in zero-result queries signals the corpus and real traffic have diverged); and a structured query log recording exactly what was retrieved for exactly which question, so a bad answer can be replayed and diagnosed later.
How An instrumented_search() wrapper times each stage separately with a precise clock, runs the hybrid search from Section 6, and appends one structured record per query — timestamp, question, filter used, result count, top score, per-stage timing in milliseconds, which embedding model produced the vectors, and whether the query came back empty ("refused"). That record is exactly the JSON line that would ship to a real log aggregator in production.
Plain English

A structured log line is a receipt for every search: what was asked, what came back, how confident it was, how long each part took. Without receipts, "something went wrong" is unfalsifiable — nobody can go back and check.

p95 latency, in plain terms

p95 latency is the time it takes for 95 out of 100 requests to finish — the slowest 5% still matter, because that slow tail is somebody's bad day, often exactly during the worst possible moment (an incident, high traffic). The notebook simulates a realistic traffic mix (the 13 evaluation questions repeated, plus genuinely out-of-scope questions like "How do I bake sourdough bread?") and computes p50/p95/p99 latency alongside the plain average — the whole point being that the average alone would hide exactly the tail that matters operationally.

The production alarm: in-scope vs. out-of-scope score separation

The simulated traffic deliberately mixes real SRE questions with clearly out-of-scope ones (TLS certificate rotation on a mail server, refund policy, sourdough bread). Plotting the top relevance score for in-scope questions against out-of-scope questions answers a very practical question: if the two distributions separate cleanly, a single fixed confidence threshold can reliably say "I don't know this." If they overlap, no constant threshold can tell them apart — which is exactly the finding that justifies building a dedicated confidence-scoring component rather than trusting one hardcoded number forever.

§9 Wiring it all into one production retrieval function
Problem All the pieces built across three notebooks — filtering, hybrid search, re-ranking, quality thresholding, logging — need to become one clean function an agent can simply call, rather than a notebook full of loose cells.
Why This is the shape a future agent framework (LangGraph, in Notebook 4) will actually call as a tool. It needs a predictable interface: give it a question, get back results and a log record, every time.
What A single pipeline: filter by metadata if requested → hybrid retrieve a wider candidate pool via the RRF query from Section 6 → re-rank that pool with the cross-encoder from Notebook 2 for a more careful final ordering → threshold out anything below a minimum confidence score → log a structured record of what happened.
How retrieve() runs hybrid search for a larger candidate set than the final answer needs, times the retrieve and re-rank stages separately, re-scores candidates with the cross-encoder, sorts by that final score, keeps only the top k above any minimum score, and returns both the results and a log record in one call. A thin answer() wrapper on top builds the final prompt for an LLM, citing chunk IDs, and explicitly instructs it to say "I don't have a runbook for that" rather than guessing when nothing qualifies.
Plain English

Why returning a log record matters, not just results

retrieve() deliberately returns results and a log record together. That shape is intentional: a future agent framework can write the log record straight into its own trace of what happened, so every retrieval decision is auditable. During a postmortem, that's the difference between "the AI was wrong" (unfalsifiable) and "retrieval returned the wrong chunk at a specific time with a specific score, here's the evidence" (fixable).

Takeaway The recurring theme across all three notebooks: every naive-looking shortcut (exact keyword matching, an in-memory index, a single crude hit@1 metric, no instrumentation) works fine on a small demo and breaks in a specific, predictable way at real scale — usually silently. Production RAG isn't a different algorithm; it's the same retrieval idea wrapped in durability, measurement, and instrumentation so those failures become visible instead of invisible.
